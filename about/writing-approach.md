# My Technical Writing Approach

## Introduction

My approach to technical writing is centred on making complex technical information clear, accurate, structured, and accessible to its intended audience.

With a background in Software Engineering, I understand that technical documentation is not simply about explaining how software works. It is about helping people use, understand, install, maintain, and troubleshoot technology with confidence.

I aim to create documentation that is practical, easy to navigate, and useful in real-world situations.

## 1. Understanding the Audience

Before writing documentation, I consider who will be using it and what they need to achieve.

Different audiences require different levels of technical detail.

| Audience | Documentation Focus |
|---|---|
| Developers | API references, architecture, setup instructions, and technical explanations |
| End users | Step-by-step user guides and workflow instructions |
| Technical support teams | Troubleshooting procedures, common errors, and resolution steps |
| System administrators | Installation, configuration, access management, and maintenance |

Understanding the audience helps me choose appropriate terminology, structure, and level of detail.

## 2. Research and Information Gathering

I begin by understanding the product, system, or process being documented.

My research process includes:

- Reviewing available technical documentation and product resources.
- Understanding the system's purpose, features, and workflows.
- Identifying the information users need to complete specific tasks.
- Checking terminology and technical details against reliable sources.
- Recording assumptions, limitations, and areas requiring further verification.

I aim to distinguish between verified product behaviour, documented information, and assumptions rather than presenting unverified details as facts.

## 3. Planning and Structuring Documentation

I organise information before drafting to ensure that documents follow a logical structure.

Depending on the purpose, I use formats such as:

- Introduction and scope
- Prerequisites
- Step-by-step procedures
- Expected results
- Examples and explanations
- Common issues and solutions
- References and additional resources

I use headings, tables, lists, code blocks, and diagrams where they improve readability and navigation.

## 4. Writing for Clarity and Usability

I prioritise straightforward language and practical explanations.

My writing principles include:

- Use clear and descriptive headings.
- Keep instructions focused on one action at a time.
- Use consistent terminology throughout a document.
- Explain technical terms when necessary.
- Include examples where they help clarify a concept.
- Avoid unnecessary jargon and overly complicated sentences.
- Make important prerequisites and warnings visible.

For procedural documentation, I aim to explain what the user needs to do, how to do it, and what they should expect afterwards.

## 5. Technical Accuracy and Validation

Accuracy is an essential part of technical writing.

Where possible, I validate documentation by:

- Following installation instructions from a clean environment.
- Checking API endpoints against the actual implementation.
- Reviewing code examples and configuration instructions.
- Comparing product workflows with official documentation.
- Checking that troubleshooting steps are relevant to the described issue.
- Updating documents when technical information changes.

When direct testing is not possible, I clearly identify the limitations and avoid claiming that instructions have been tested.

## 6. Documentation Tools and Version Control

I use documentation tools that support structured writing, collaboration, and maintenance.

| Tool | Purpose |
|---|---|
| Markdown | Writing structured technical documentation |
| GitHub | Hosting documentation and managing version history |
| Visual Studio Code | Creating and editing documentation files |
| Git | Tracking changes and maintaining documentation versions |
| Swagger / OpenAPI | Exploring and documenting REST APIs |

I am also developing my knowledge of professional documentation platforms and structured authoring tools.

My portfolio explores how technical writing can be adapted to different technical environments.

My documentation includes:

- Project overview

## 8. Continuous Improvement

I consider documentation an ongoing process rather than a one-time writing task.

I aim to improve my work through:

- Reviewing and editing existing documents.
- Incorporating feedback from readers and reviewers.
- Identifying missing or unclear information.
- Keeping documentation aligned with software changes.
- Learning new documentation tools and industry standards.
- Studying documentation practices across different industries.

## Conclusion

My goal as an aspiring technical writer is to bridge the gap between technical systems and the people who use them.

I combine my Software Engineering knowledge with structured writing and research to produce documentation that is understandable, accurate, and practical.

Through projects such as Sastagram and OpenMRS, I am developing the ability to communicate technical information across different domains while continuously improving my documentation skills.
